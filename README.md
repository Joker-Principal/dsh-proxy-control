# dsh-proxy-control

在运行中控制 **DeepSeek Harness** 的出站代理：一个设置页、三种地址来源、Windows 系统代理探测、连通性自测，**改动立即生效，不用重启**。

[English](README.en.md) ｜ 中文

```
设置 → 代理
```

## 特性

- **三种地址来源，互斥**：内置（DSH 启动环境）/ 系统（Windows 代理设置）/ 手动（自己填）。
- **改动立即生效**：切来源、改地址、改直连名单，下一次请求就按新配置走，不需要重启应用。
- **如实的状态**：界面显示的是此刻**实际会怎么走**，而不是"插件装了什么"。
- **连通性自测**走真实调用路径，回报"配置说会怎样"和"实际怎样"，直连也是一种有效结果。
- **简单分流**用直连名单表达（例如让模型与搜索直连、其余走代理）。

## 安装

要求 **DSH 0.2 系列**（Desktop 或 CLI）与 Node.js **22+**。

插件以目录形式安装到某个 profile：

```sh
# CLI
dsh plugin --profile desktop add "/绝对路径/dsh-proxy-control"
```

也可以在界面里：**设置 → 插件 → 添加插件**，选择本插件目录。

安装后**重启一次**（profile 的 bundle 列表只在启动时读）。这一次重启之后，之后所有代理改动都是实时的。

本包声明了 `dsh.bundle.patch`（`cordis.patch.yml`），所以插件条目会被自动插入 profile，并带上初始配置。也可以绕过界面直接编辑 profile 的 `cordis.patch.yml`：

```yaml
- id: proxy-control
  name: dsh-proxy-control
  config:
    mode: env          # env 内置 / system 系统 / manual 手动
    proxy: ''          # 仅手动模式使用
    noProxy: ''        # 直连名单（简单分流）
    testUrl: ''        # 留空用默认自测地址
```

> 早先版本用过 `enabled`（总开关）与 `autoDetect` 两个字段，现在都已删除 —— 它们与"内置"来源重复。配置里如果还留着，插件会忽略，并在下次保存时自动清掉。

## 配置项

| 配置项 | 说明 |
|---|---|
| 代理来源 | **三选一**：`内置` / `系统` / `手动`。默认 `内置` —— 它是**惰性**的，装上插件不会改变任何行为。 |
| 代理地址 | 仅手动模式生效。例如 `http://127.0.0.1:7890`。只接受 `http://` 与 `https://`。 |
| 直连名单 | 简单分流：这里的主机不走代理。仅手动/系统模式生效；内置模式以环境里的 `NO_PROXY` 为准。 |
| 自测地址 | 「测试」按钮访问的地址，留空用 `https://www.gstatic.com/generate_204`。 |

## 三种地址来源

| 界面上的名字 | 从哪读 | 什么时候用 |
|---|---|---|
| **手动** | 你在界面上填的地址 | 最常见 |
| **系统** | Windows 注册表 `Internet Settings`（不解析 PAC） | 代理软件开了"系统代理"，你不想每次手动同步端口 |
| **内置** | **启动环境**：`$DSH_HOME/.env` 或启动前导出的变量 | 你已经在 `.env` 里配了代理，希望插件不插手、只如实显示它（默认值） |

### 为什么要「内置」这一项

Harness 只在启动时解析一次代理策略：

```
dsh-desktop-host → runProfile()
    → installProxyFromEnvironment(loadLayeredEnv("dsh"))   ← 策略在这里定死
    → boot(...) → 你的插件开始挂载                          ← 插件从这之后才活着
```

也就是说，内置方式改代理的唯一办法是编辑 `$DSH_HOME/.env` 然后重启。本插件在运行中重新执行同一次安装，配置来自它自己的条目，所以在设置页里改地址，**下一次请求就生效**。

### 两层策略：为什么不插手时也可能在走代理

**启动器那层和插件这层是两层，各自独立。**

- 启动器那层在插件挂载前就装好了。如果你把代理写进了 `.env` 或启动前导出过变量，那层就是**活的**。
- 插件只能管自己这一层。选「内置」时插件**什么都不装**，释放的也只是插件这层 —— **启动器那层照旧生效**。

所以"插件不管事就等于直连"是错的。这个事实必须被如实显示出来，而不是让界面猜：设置页里那句「生效中的代理」会点名**是哪一层**在起作用：

```
生效中的代理：http://127.0.0.1:7890（启动环境（.env 或已导出的变量））
```

括号里是「本插件的配置」时，说明是插件在路由；是「启动环境（.env 或已导出的变量）」时，说明在生效的是启动器那层。没有代理时这句就写「生效中的代理：直连」。

两个细节：

- **`.env` 只在启动时读一次**，所以改 `.env` 仍然要重启；内置模式不会让它变成热更新。
- 官方解析器有个真实行为你会原样看到：**只设 `HTTPS_PROXY` 时，`http://` 目标仍然直连**。想两者都走代理，就把 `HTTP_PROXY` 一起写上。

## 「测试」测的是配置的效果

按钮走的是 **Harness 自己的调用路径**：全局 `fetch()` —— 也就是 LLM 请求、web 搜索、HTTP MCP 用的那条。所以它回答的是"你的配置生效后会怎样"，而不是"这个代理能不能用"。

结果就显示在**自测地址那一行的下方**，同时给两件事：

```
连通 · 经由 http://127.0.0.1:7890 · 204 · 120 毫秒
连通 · 直连 · 204 · 80 毫秒
不通 · 经由 http://127.0.0.1:7890 · <错误>
```

- **路由**是配置对这个测试地址的判定 —— 协议不同答案可能不同（只设 `HTTPS_PROXY` 时 `http://` 目标会直连）。
- **结果**是真的发出去之后拿到的状态码与耗时。

**直连也是一种有效结果**，照样报出来：配置就是直连时，"能不能直连上"同样是你想知道的。

两点说明：

- 它测的是**你眼前这份配置**：点按钮前若有还没落盘的改动（比如刚改完地址就顺手点测试），会先把它写下去再测 —— 否则结果会一本正经地报出一个你已经改掉的地址。
- 接口**不接受**"临时指定一个代理来测"。早先的版本可以，但那测出来的是代理的可用性，不是配置的效果。

## 界面说明

- 三行来源（内置 / 系统 / 手动）**常驻显示**，未选中的那几行只是置灰并标一句「未选中」—— 这样能同时看到另几个来源此刻是什么，也能看清"切换会拿走哪些字段"。切换来源时会顺手**强制重读**那一边（它们的值都是在别处编辑的），拿到的是此刻的值而不是缓存。
- 内置与系统那两行**只显示结果**：读到代理就显示代理服务器，没有就显示「直连」。为什么是直连、去哪打开它，都在标题旁的 `?` 里（悬停或键盘聚焦展开）；长说明里可以用换行分段。
- 三个动作是**图标按钮**，功能写在悬停提示里（按钮上仍带 `aria-label`，键盘与读屏都能用）：内置、系统两行各一个环形箭头（重新读取 / 重新探测），自测地址输入框后面一个信号图标（测试）。
- **没有「保存」按钮**：手打的三个字段在**失去焦点时自动落盘**，回车也行。切来源、重新读取、测试都是点了就生效，只有这三个字段需要额外按一下按钮，那种不一致比"忘了保存"更容易出错。反过来，**失焦只保存，绝不触发测试**。
- **三处"读出来的结果"都显示在各自那一行的下方**（内置的来源、生效中的代理、自测结果）—— 另起一段会被分隔线割开，塞进主行又会让右侧控件上下跳。

## 覆盖范围

插件驱动的是运行时自己的策略模块，所以覆盖范围和 DSH 启动时装的那份**完全一致**：

| 流量 | 走代理 |
|---|---|
| LLM 对话、web 搜索、HTTP MCP（都走全局 `fetch`） | ✅ |
| 联网抓取 `web_fetch` | ✅ 它问的是同一份策略，答"走代理"才改用显式 dispatcher |
| 子进程：bash / pwsh / curl / git / pnpm | ✅ 安装策略时会发布 `HTTP_PROXY`/`HTTPS_PROXY` 与 `NODE_USE_ENV_PROXY=1` |
| 回环地址（本地 Web UI、Connection） | ❌ 策略强制直连 `localhost`、`127.0.0.0/8`、`::1`、`0.0.0.0` |
| OTEL 遥测、`ws` 远程连接、PTC/workflow worker | ❌ 上游设计上不走代理 |
| Electron/Chromium 自身流量（自动更新、欢迎页、登录页） | ❌ 另一个进程的网络栈，插件碰不到 |

**一处插件层修不了的不对称**：策略模块把"最外层安装时的环境变量"记在自己的私有状态里，没有 API 能改。所以当 `.env` 里也配了代理时，**子进程会跟随 `.env` 那份值，而本进程内按插件的配置走**。插件会在界面与日志里提示这个分叉；想消除歧义就只留一个来源，或者干脆把来源选成「内置」让两者同源。

## 关于分流：为什么没有按类别开关

你可能会想要「LLM 走代理、web_fetch 不走」这类开关。**在这套运行时里做不到，而且不该做**，有两个硬约束：

1. **LLM 对话和 web 搜索是同一个 URL。** 两者最终都是 `https://api.deepseek.com/anthropic/v1/messages`，在传输层无法区分（唯一差异在请求体里，dispatcher 看不到）。
2. **联网抓取的代理与子进程绑死。** 官方策略一装上就会把代理变量发布给所有子进程，**联网抓取开 → 子进程必然继承代理，关不掉。**

所以"简单分流"用**直连名单**表达，它准确、可预期：

```
直连名单：api.deepseek.com        # 模型与搜索直连、联网抓取与 MCP 走代理
```

真正细的分流（域名规则、GeoIP、进程名）交给代理软件自己 —— 它能看到的信息比这一层多得多，两套规则引擎并存只会让你在出问题时不知道是谁决定的。

## 已知限制

- **不支持 SOCKS。** 官方策略只接受 `http:`/`https:`，而 SOCKS 覆盖不到联网抓取。填 SOCKS 会被明确拒绝并说明原因，不会静默忽略。
- **不做按类别开关**，原因见上。
- **系统代理只在选中「系统」时才是地址来源**，并且是在启动、每次改配置、以及点那一行的**重新探测**图标时读取。你在系统里换了代理端口，需要点一次它。**不解析 PAC**（会报告出来）。
- **系统 bypass 列表被整份忽略**：Windows 那边大量是 `127.*`、`192.168.*`、`<local>` 这类通配写法，而本 Harness 的匹配器只做主机名后缀比较，照搬会变成一堆永不匹配的垃圾条目。回环地址本来就被强制直连。
- **直连名单不支持 CIDR**（`10.0.0.0/8` 这类会被丢弃并提示）。
- **不支持自定义证书颁发机构。** 做 TLS 拦截的企业代理需要在启动前设 `NODE_EXTRA_CA_CERTS`。
- **Electron 的 Chromium 流量碰不到** —— 见覆盖范围表。

## 安全性

设置页用的那几个接口能改写"流量往哪走"，所以它们有三重限制：**只接受来自本机的请求**、**`Host` 必须是回环地址**（挡 DNS 重绑定），并且**不接受能免预检跨站发送的请求体形态**（挡普通网页发起的跨站请求，其响应码为 403 / 415）。

这样做的原因是 DSH 的 Web 服务器本身不携带认证或来源策略，第三方路由必须自己设防；否则你访问的任何网页都能把出站流量改道到它自己的代理上。

## 排错

**界面上**：「代理来源」那一行下方那句「生效中的代理」是权威读数，括号里会点名是哪一层在生效。

**在 shell 里**（可以让 agent 自己跑）：

```powershell
$env:HTTPS_PROXY; $env:NODE_USE_ENV_PROXY
```

这两个**只有在策略已安装时**才会被发布给子进程，所以它是活体读数，而不是配置文件回显。

**日志里**：

```
proxy-control：出站请求经由 http://127.0.0.1:7890（手动指定），直连名单 api.deepseek.com
proxy-control：不干预路由（启动环境里没有代理设置（查过 C:\Users\Joker\.dsh\.env），按直连处理）
proxy-control：不干预路由（启动环境里有 http://127.0.0.1:7890，插件不插手（那就是启动器那层在生效））
proxy-control：无法使用 <地址>（<原因>），出站请求保持直连
```

**两条行为保证**：

- **用不了的代理绝不弄死 agent。** SOCKS、非法 URL、不支持的协议都会记一行警告并保持直连，进程照常运行。
- **卸载插件会还原启动器自己的策略**，因为它是在那之上加了一层，而不是替换。
